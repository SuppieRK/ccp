# public-release-distribution Specification

## Purpose
Define tag-driven public binary distribution for `ccp` with stable multi-platform artifacts, integrity metadata, installer/upgrade asset-contract compatibility, and release smoke validation.
## Requirements
### Requirement: Tagged Multi-Platform Release Artifacts
The project SHALL publish versioned release artifacts from git tags for Linux, macOS, and Windows across `amd64` and `arm64` targets.

#### Scenario: Release artifacts are produced from a tag
- **WHEN** a release tag is pushed
- **THEN** CI builds and publishes platform-specific `.zip` archives for supported OS/architecture targets.

#### Scenario: Existing release tag is not overwritten
- **WHEN** a release workflow runs for a tag that already has published assets
- **THEN** the workflow fails instead of overwriting existing release artifacts.

### Requirement: Integrity Metadata for Releases
Each published release SHALL include checksum metadata for distributed artifacts.

#### Scenario: Checksums are available for verification
- **WHEN** release artifacts are published
- **THEN** checksum files are published alongside artifacts and can be used to validate downloaded binaries.

#### Scenario: Checksums are generated by release configuration
- **WHEN** release artifacts are built for a tag
- **THEN** checksum metadata is generated by the release workflow using SHA-256
- **AND** the checksum filename contract remains aligned with `.goreleaser.yaml` checksum configuration
- **AND** checksum outputs match the published binary archive artifacts.

### Requirement: Distribution Asset Naming Contract
The published asset naming contract SHALL remain stable for distribution clients (installer and upgrade flows) without redefining installer behavior.

#### Scenario: Asset naming preserves release tag format
- **WHEN** distribution clients resolve artifact names from a release tag (for example `1.2.3`)
- **THEN** the `<version>` segment in `ccp_<version>_<os>_<arch>.zip` matches the release tag format used by published assets.

#### Scenario: Platform and archive contract is stable
- **WHEN** release artifacts are published
- **THEN** each supported OS/architecture target is emitted as `.zip` using normalized identifiers in the filename contract.

### Requirement: Release Smoke Validation
Release CI SHALL include a smoke-install validation that downloads a published artifact and verifies executable startup.

#### Scenario: Smoke install succeeds
- **WHEN** release workflow runs post-publish validation
- **THEN** a downloaded artifact executes `ccp --version` successfully.

### Requirement: Upgrade Command Uses GitHub Releases
The `ccp upgrade` command SHALL resolve release binaries from GitHub Releases and perform in-place self-update without requiring a local source path argument.

#### Scenario: Upgrade latest from releases
- **WHEN** a user runs `ccp upgrade` with no explicit version
- **THEN** `ccp` resolves the latest compatible release asset from GitHub Releases and updates the local binary in place.

#### Scenario: Upgrade specific release tag
- **WHEN** a user runs `ccp upgrade --version <tag>`
- **THEN** `ccp` resolves the matching tagged release asset from GitHub Releases and updates the local binary in place.

#### Scenario: Upgrade preserves executable permissions after ZIP extraction
- **WHEN** `ccp upgrade` installs a downloaded binary from a `.zip` archive on Unix-like systems
- **THEN** the final executable is marked runnable before completion.

### Requirement: Atomic and Resilient Upgrade
The `ccp upgrade` command SHALL leave the current binary untouched when download or release resolution fails.

#### Scenario: Upgrade fails on release API or download error
- **WHEN** `ccp upgrade` cannot resolve or download a release asset
- **THEN** it exits with code `1`, prints a user-friendly error, and keeps the currently installed executable unchanged.

### Requirement: Binary Archive Provenance Attestations
Public release distribution SHALL include provenance attestations for released binary archives.

#### Scenario: Release publishes attestations for binary archives
- **WHEN** a tagged release publishes binary archive assets
- **THEN** the workflow runs GitHub `actions/attest` to generate attestations for those binary archive assets.

#### Scenario: Non-binary release files are excluded from attestation subjects
- **WHEN** checksum files or auxiliary release metadata are present in the release outputs
- **THEN** those files are not selected as attestation subjects.
